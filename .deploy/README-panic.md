# Тревожная кнопка

**Настройки → Протокол AID → «Запустить протокол AID»**. Видна Создателю, Директору и Менеджеру, сервер проверяет роль сам.

Порядок: три подтверждения (кнопка каждый раз в другом месте), затем PIN.

**Неверный PIN.** Окно просто закрывается, и ничего не происходит. После 3 неверных PIN кнопка не срабатывает час, даже с верным PIN.

**Верный PIN.** Происходит следующее:

1. Вся база шифруется вашим открытым ключом в `data/panic/<дата>/database.sql.gz.enc`.
2. CRM переходит в **облегчённый режим** и остаётся рабочей. Из базы удаляются:
   - **записи**, кроме активных с сегодняшнего дня и закрытых без наличных (оплата по РС, картой, юрлица). Если в оплате была хоть часть наличными или валютой, запись удаляется. Прошедшие незакрытые, отменённые и перенесённые из старой программы тоже удаляются;
   - **клиенты и машины**, которых нет в оставшихся записях;
   - **сотрудники**, кроме Создателя, Директора и Менеджера (уволенные — все). Их зарплаты, оклады, премии, штрафы и переносы ЗП тоже удаляются;
   - **касса**, кроме приходов оставшихся записей. Эти приходы и сделки переводятся в РС. Удаляются также капитал, ЗП учредителей, заказы VDF и помесячная статистика;
   - **вики**, заявки с сайта, все заметки, категории расходов, источники клиентов, журнал изменений денег, SMS-журнал и пуш-подписки;
   - закупочные цены товаров склада.
3. Все устройства выходят из аккаунта. При выходе телефон удаляет кеш данных. Устройство, которое сейчас выключено, очистит кеш при следующем открытии CRM.
4. Удаляются все бэкапы в `/root/backups/prime-crm`.
5. Фоном шифруются все файлы в `data/panic/<дата>/uploads.tar.gz.enc`. Затем удаляются фото удалённых записей, фото заявок и файлы вики.
6. Тот же протокол запускается в магазине **vdf.by**: CRM дёргает `VDF_URL/api/integrations/panic/` с общим ключом и тем же PIN. VDF шифрует и чистит свою базу сам (покупатели, заказы, заявки, бухгалтерия, себестоимость, копии). Восстановление VDF — `docs/panic-protocol.md` в проекте магазина, тем же приватным ключом.

Нажатие в самом магазине тоже запускает оба сервиса: VDF дёргает CRM. Срабатывание из интеграции идёт без обратной передачи — по кругу сервисы друг друга не вызывают.

**Облегчённый режим** (`SecurityState.liteMode`, сервер — `src/utils/liteMode.ts`):

- **Вход.** Входят только Создатель, Директор, Менеджер и мастер-доступ.
- **Скрыто.** Дашборд, вики, приходно-расходный, VDF, капитал, расчёт ЗП, ЗП учредителей и статистика. В настройках — категории расходов, сотрудники, мастера приёмщики, клиенты, источники клиентов, открытые возможности, упущенная прибыль и сам протокол AID (повторный запуск после срабатывания закрыт). Сервер отвечает на эти адреса 404.
- **Оплата.** «Приход РС» называется просто «Приход». Все приходы — по РС: при закрытии сделки, в предоплате и при отмене нет выбора наличных, раздельной оплаты и валюты.
- **Записи.** Нет полей «Сотрудник», «Мастер приёмщик» и «Источник клиента». Закрыть сделку можно без источника.
- **Работает как раньше.** Расписание, заявки (новые принимаются как обычно), долги, почта, заметки, услуги, типы ремонта, склад, справочник авто, SMS, шаблоны и настройки компании.

Режим выключается сам при восстановлении базы из архива: архив снят до очистки.

Если зашифровать базу не удалось, **ничего не удаляется**. Вы при этом остаётесь в аккаунте: так видно, что кнопка не сработала. Причина записана в логах: `docker compose logs server | grep panic`.

## Настройка (один раз)

На **своём компьютере**, в папке `server` проекта:

```
npm run panic:keygen
```

Скрипт выводит два ключа:

- **Открытый ключ** (`PANIC_PUBLIC_KEY=…`) — в `.env` на сервере.
- **Приватный ключ** — переписать на бумагу, в два надёжных места. На сервере, в git, мессенджерах, почте и облаке его быть не должно. Без него данные не восстановить.

```
npm run panic:pin
```

PIN вводится скрыто. Скрипт выводит `PANIC_PIN_HASH=…`, это тоже в `.env` на сервере.

Те же `PANIC_PUBLIC_KEY` и `PANIC_PIN_HASH` кладутся и в `.env` магазина vdf.by — ключ восстановления и PIN общие на оба сервиса. Для передачи CRM→VDF в `.env` CRM должен быть `VDF_URL` (по умолчанию `https://vdf.by`) и общий `VDF_INTEGRATION_KEY`.

На сервере:

```
cd /var/www/prime-crm
nano .env                       # добавить PANIC_PUBLIC_KEY и PANIC_PIN_HASH
docker compose up -d --build server
docker compose logs server | grep -i "тревожная"   # пусто — кнопка настроена
```

Сменить PIN можно только через `.env` на сервере. Через интерфейс его не поменять.

## После срабатывания

Сразу скачайте архив к себе: он лежит только на сервере. Без ключа он бесполезен, поэтому хранить его можно где угодно.

```
scp -r root@93.125.12.160:/var/www/prime-crm/data/panic .
```

## Восстановление

1. **На своём компьютере** расшифруйте архив. Приватный ключ вводится скрыто, пробелы можно оставить как на бумаге:

   ```
   cd server
   npm run panic:decrypt -- ..\panic\<дата>
   ```

   Рядом с `.enc` появятся `database.sql.gz` и `uploads.tar.gz`. Это **открытые данные**: после восстановления их нужно удалить.

2. Загрузите файлы на сервер:

   ```
   ssh root@93.125.12.160 mkdir -p /root/restore
   scp ..\panic\<дата>\database.sql.gz ..\panic\<дата>\uploads.tar.gz root@93.125.12.160:/root/restore/
   ```

3. **На сервере** восстановите базу и файлы:

   ```
   cd /var/www/prime-crm
   docker compose stop server
   docker compose exec -T postgres dropdb -U postgres prime_crm
   docker compose exec -T postgres createdb -U postgres prime_crm
   gunzip -c /root/restore/database.sql.gz | docker compose exec -T postgres psql -U postgres -d prime_crm -v ON_ERROR_STOP=1 -q
   tar -xzf /root/restore/uploads.tar.gz -C data/uploads
   ```

4. **Смените `JWT_SECRET`** в `.env` (`openssl rand -hex 32`). В восстановленной базе нет отметки «все вышли». Без смены секрета старые токены снова заработают, в том числе украденные.

   ```
   docker compose up -d server
   rm -rf /root/restore
   ```

   Затем удалите расшифрованные `database.sql.gz` и `uploads.tar.gz` у себя на компьютере.

## Ограничения

- **Взлом сервера с root-доступом.** Кнопка не спасает, если сервер взломали с root-доступом: тогда данные можно забрать до нажатия.
- **Следы на диске.** Удалённые файлы и старые журналы базы на диске VPS какое-то время можно восстановить специальными средствами. Кнопка делает всё, что можно сделать изнутри: `TRUNCATE`, `VACUUM`, `CHECKPOINT`.
- **Логи.** Логи запросов (`docker compose logs`) не очищаются. Данных клиентов и сумм в них нет, есть только адреса запросов и имена сотрудников.
