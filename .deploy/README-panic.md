# Тревожная кнопка

**Настройки → Протокол AID → «Запустить протокол AID»**. Видна Создателю, Директору и Менеджеру, сервер проверяет роль сам.

Порядок: три подтверждения (кнопка каждый раз в другом месте), затем PIN.

**Неверный PIN.** Показывается «Протокол недоступен», и ничего не происходит. После 3 неверных PIN кнопка не срабатывает час, даже с верным PIN.

**Верный PIN.** Происходит следующее:

1. Вся база шифруется вашим открытым ключом в `data/panic/<дата>/database.sql.gz.enc`.
2. Из базы удаляются клиенты, авто, записи, сделки, касса, капитал, долги, зарплаты и оклады, помесячная статистика, журнал изменений денег, заметки, SMS-журнал и пуш-подписки. У товаров склада стираются закупочные цены.
3. Все устройства выходят из аккаунта. При выходе телефон удаляет кеш данных. Устройство, которое сейчас выключено, очистит кеш при следующем открытии CRM.
4. Удаляются все бэкапы в `/root/backups/prime-crm`.
5. Фоном шифруются все файлы в `data/panic/<дата>/uploads.tar.gz.enc`, затем удаляются фото записей.

**Что остаётся:** справочники (услуги, оборудование, авто, категории расходов), сотрудники и их входы, настройки компании, шаблоны документов, вики, склад (без цен).

Если зашифровать базу не удалось, **ничего не удаляется**. Вы при этом остаётесь в аккаунте: так видно, что кнопка не сработала. Причина записана в логах: `docker compose logs server | grep panic`.

## Настройка (один раз)

На **своём компьютере**, в папке `server` проекта:

```
npm run panic:keygen
```

Скрипт выводит два ключа:

- **Открытый ключ** (`PANIC_PUBLIC_KEY=…`) — в `.env` на сервере.
- **Приватный ключ** — переписать на бумагу, в два надёжных места. На сервере, в git, мессенджерах, почте и облаке его быть не должно. Без него данные не восстановить.

```
npm run panic:pin
```

PIN вводится скрыто. Скрипт выводит `PANIC_PIN_HASH=…`, это тоже в `.env` на сервере.

На сервере:

```
cd /var/www/prime-crm
nano .env                       # добавить PANIC_PUBLIC_KEY и PANIC_PIN_HASH
docker compose up -d --build server
docker compose logs server | grep -i "тревожная"   # пусто — кнопка настроена
```

Сменить PIN можно только через `.env` на сервере. Через интерфейс его не поменять.

## После срабатывания

Сразу скачайте архив к себе: он лежит только на сервере. Без ключа он бесполезен, поэтому хранить его можно где угодно.

```
scp -r root@217.12.37.199:/var/www/prime-crm/data/panic .
```

## Восстановление

1. **На своём компьютере** расшифруйте архив. Приватный ключ вводится скрыто, пробелы можно оставить как на бумаге:

   ```
   cd server
   npm run panic:decrypt -- ..\panic\<дата>
   ```

   Рядом с `.enc` появятся `database.sql.gz` и `uploads.tar.gz`. Это **открытые данные**: после восстановления их нужно удалить.

2. Загрузите файлы на сервер:

   ```
   ssh root@217.12.37.199 mkdir -p /root/restore
   scp ..\panic\<дата>\database.sql.gz ..\panic\<дата>\uploads.tar.gz root@217.12.37.199:/root/restore/
   ```

3. **На сервере** восстановите базу и файлы:

   ```
   cd /var/www/prime-crm
   docker compose stop server
   docker compose exec -T postgres dropdb -U postgres prime_crm
   docker compose exec -T postgres createdb -U postgres prime_crm
   gunzip -c /root/restore/database.sql.gz | docker compose exec -T postgres psql -U postgres -d prime_crm -v ON_ERROR_STOP=1 -q
   tar -xzf /root/restore/uploads.tar.gz -C data/uploads
   ```

4. **Смените `JWT_SECRET`** в `.env` (`openssl rand -hex 32`). В восстановленной базе нет отметки «все вышли». Без смены секрета старые токены снова заработают, в том числе украденные.

   ```
   docker compose up -d server
   rm -rf /root/restore
   ```

   Затем удалите расшифрованные `database.sql.gz` и `uploads.tar.gz` у себя на компьютере.

## Ограничения

- **Взлом сервера с root-доступом.** Кнопка не спасает, если сервер взломали с root-доступом: тогда данные можно забрать до нажатия.
- **Следы на диске.** Удалённые файлы и старые журналы базы на диске VPS какое-то время можно восстановить специальными средствами. Кнопка делает всё, что можно сделать изнутри: `TRUNCATE`, `VACUUM`, `CHECKPOINT`.
- **Логи.** Логи запросов (`docker compose logs`) не очищаются. Данных клиентов и сумм в них нет, есть только адреса запросов и имена сотрудников.
